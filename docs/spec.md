# Проект AI-ассистент с RAG (retrieval-augmented generation)

**Стек:** Next.js · провайдер-независимый AI-слой с переключаемыми OpenAI / Anthropic+Voyage / Gemini адаптерами (chat completion + embeddings) · Supabase Postgres с расширением `pgvector` · Vercel AI SDK (для стриминга) · TypeScript.

**Дополнительное УТП проекта:** архитектура не завязана на одного AI-вендора — провайдер переключается переменной окружения `AI_PROVIDER`, без изменений в бизнес-логике. Это для пользователей, которые не хотят vendor lock-in или у которых уже есть контракт/кредиты с конкретным провайдером. Второе УТП — источники знаний не ограничены загрузкой файлов: Notion, публичные страницы, Google Drive.

**Функционал MVP:**
1. Добавление документов из нескольких источников: ручная загрузка (PDF/markdown/txt), импорт из Notion (по ссылке на страницу/базу, через Internal Integration Secret), импорт по публичному URL, синхронизация папки Google Drive (через Service Account). Оригиналы/кэш текста — в Supabase Storage.
2. Чанкинг текста (например, по 500-800 токенов с overlap) и генерация embeddings — едиными для всех источников, через активный AI-провайдер.
3. Сохранение chunks + embeddings в Postgres (`pgvector`, индекс `ivfflat` или `hnsw`).
4. Чат-интерфейс: вопрос пользователя → embedding запроса → similarity search (top-k) → сборка контекста → запрос к chat completion со стримингом ответа в UI.
5. Отображение источников ("на основе документа X, стр. Y" / "из Notion-страницы Y" / "со страницы by URL") под каждым ответом — это то, что реально продают клиентам под видом "AI knowledge base".
6. История переписки, сохранённая в Supabase, привязанная к пользователю.
7. Ручная ре-синхронизация документа из внешнего источника (кнопка "Refresh") — без автоматического поллинга/вебхуков в MVP.

**Best practices:**
- System prompt явно ограничивает модель отвечать **только** на основе найденного контекста ("если ответа нет в контексте — скажи, что не знаешь").
- Ограничение стоимости: лимит длины контекста, лимит запросов в минуту на пользователя (rate limiting), логирование токенов на запрос.
- Обработка ошибок AI-провайдера (429/500) с retry и понятным сообщением пользователю, единообразная независимо от того, какой провайдер активен.
- Вызовы LLM и embeddings изолированы за интерфейсами `ChatProvider`/`EmbeddingsProvider` — конкретные SDK (OpenAI/Anthropic/Voyage/Gemini) не используются напрямую в бизнес-логике.
- Разумный размер чанков — не по абзацам "на глаз", а с тестами на качество поиска (пара примеров "вопрос → ожидаемый источник" в README как демонстрация точности).
- Стриминг ответа через Server-Sent Events/Vercel AI SDK, а не ожидание полного ответа.
- Источник "публичный URL" защищён от SSRF (запрет приватных/link-local адресов, проверка редиректов, лимиты таймаута и размера) — сервер сам ходит по адресу, который ввёл пользователь, и это отдельная категория уязвимости, которую нужно закрыть явно, а не понадеяться, что "никто так не попробует".
- Токены источников на пользователя (Notion Integration Secret) хранятся зашифрованными, не открытым текстом в БД.

## Общие правила (из общего документа со спецификациями, применимы и здесь)

- **TypeScript strict mode** включён везде, без `any` без необходимости.
- **Секреты только в `.env`**, добавлен `.env.example` с плейсхолдерами. Ни один ключ не закоммичен в историю git.
- **README по единому шаблону**: что делает проект → стек → живое демо (ссылка) → как запустить локально (`git clone` → `npm i` → `.env` → `npm run dev`) → скриншоты/GIF → ключевые технические решения (2-3 абзаца — почему так, а не иначе).
- **Демо-доступ для прользователя**: тестовый логин/пароль или "Try demo" кнопка без регистрации, плюс 1-2 готовых тестовых документа уже загруженных в демо-аккаунт, чтобы пользователь сразу мог задать вопрос, не загружая свои файлы.
- **Обработка ошибок и edge cases** — не happy-path-only код: пустые состояния, невалидный ввод, таймауты, retry там где уместно.
- **Минимум тестов** — хотя бы несколько unit/integration тестов на критичную логику (чанкинг, similarity search RPC, rate limiter). Наличие папки `tests/` само по себе продающий сигнал.
- **CI на GitHub Actions** — простой workflow (lint + test) на пуш. Значок "build passing" в README сильно повышает доверие.
- **Деплой на Vercel**, публичная рабочая ссылка обязательна.
- **Коммит-история осмысленная**, а не один коммит "initial commit". Делайте по фичам.
